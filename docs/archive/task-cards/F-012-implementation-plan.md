# 待生效归档实施计划：F-012 街区探索与情境对话

状态：`COMPLETE_ON_PR_MERGE`

> Step 0—4、本地统一质量、用户试玩、真实模型 UAT 和 PR #17 首次 HEAD CI 已完成；本归档随最终 PR HEAD CI 通过并合并到 `main` 后生效。

## Step 0：视觉与交互契约，0.5～1 个工作日

- 基于现有 Godot 画面设计一张 640×360 观察卡正常状态。
- 冻结三个地标的名称、固定观察、对应 NPC、交互距离、提示文案和草稿文本。
- 确认观察卡、现有对话面板和“话题与记忆”菜单不会同时争夺同一区域。
- 产物：`docs/design/contextual-exploration/design-spec.md` 与真实 Godot 首状态截图。
- 门禁：用户批准观察卡的位置、大小、文字层级和操作流程后才进入完整实现。

## Step 1：统一可交互目标，1～2 个工作日

- 将当前“最近 NPC”选择扩展为统一的最近可交互目标，但保留 NPC 身份白名单和失败关闭行为。
- 建立三个固定地标实例及稳定 ID、显示名、观察文本和对应 NPC 映射。
- 同一时刻只渲染一个提示；超范围、未知 ID 和无效映射均不产生交互。
- 地标只复用现有场景元素和 UI 样式，不下载或生成美术素材。
- 完成标准：玩家能稳定选择 NPC 或地标，碰撞、摄像机和现有对话入口不退化。

## Step 2：观察卡与启动期发现状态，1～1.5 个工作日

- 实现观察卡的打开、关闭、移动锁定、记下成功和重复查看状态。
- 发现状态只保存在当前 Godot 启动期间，并按固定地标与对应 NPC 隔离。
- 关闭或 `Esc` 不保存；“记下话题”幂等，重复操作不追加状态或声音。
- 后端不可用时该本地流程仍可完成。
- 完成标准：三地标的记录、取消、重复查看和重启清空行为符合任务卡。

## Step 3：情境对话接入，1～1.5 个工作日

- 在对应 NPC 的既有菜单中按发现状态显示“讨论街区发现”。
- 选择后只填入冻结草稿；玩家编辑后的当前输入框内容才是实际 Dialogue v1 载荷。
- 重试继续复用既有 DialogueClient 冻结请求语义，不增加隐藏字段或不可见 prompt。
- 保持三 NPC 会话、历史、关系、长期事实和发现状态互相隔离。
- 完成标准：Fake Provider 下可依次检查地标、记录、与对应 NPC 讨论并返回探索。

## Step 4：验证与用户验收，1～2 个工作日

- 扩展 Godot 场景测试：最近目标、距离/平局、移动锁定、取消、幂等、映射、重启清空和未知 ID。
- 扩展 Fake HTTP 回环：可见文本即载荷、编辑后发送、精确重试、跨 NPC 隔离和后端不可用恢复。
- 运行受影响回归，再运行统一质量入口；首次失败保留证据，定位后才修复和复验。
- 用户按三地标完整流程试玩，确认可读性、目标选择、探索节奏和对话衔接。
- 真实模型 UAT 已通过：每名 NPC 一次情境理解、一次 Persona/关系一致性，共 6 项；实际 8 次调用，2 次语义补测，未超过调用与费用硬上限。

## Step 5：文档与 Git 交付，0.5～1 个工作日

- 已分别记录静态/自动、Fake、用户视觉与手感、真实模型 UAT 结果。
- 已更新当前状态、进度和证据；任务在 Git 合并与归档前仍保持活动状态。
- 完整验收后再申请 commit、push、PR、CI、合并和归档授权。
- 保留 F-012 分支与验收资源；Codex 不删除资源。

## 实施顺序的理由

先验证 640×360 信息层级，再改变交互目标选择；随后完成纯本地观察闭环，最后才接入既有对话。这样每一步都有玩家可观察产物，且任何问题都能定位在场景交互、客户端状态或已有对话链路中的一个明确层级。
